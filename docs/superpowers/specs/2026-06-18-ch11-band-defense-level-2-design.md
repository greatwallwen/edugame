# 第 11 章塔防第 2 关设计：手环夜跑数据异常

## 1. 目标

第 2 关承接 `ch11-band-defense` 灰盒 MVP 的核心循环，不更换游戏类型、不新增复杂系统，重点把第 1 关的“认识克制关系”推进到“根据症状判断知识点”。

本关希望玩家练习：

- 区分 I2C 配置错误、运动噪声、假峰值、功耗尖峰。
- 根据波前症状选择建塔和升级顺序。
- 通过波后诊断理解自己是知识点判断错误，还是资源分配不足。

关卡中文名：

```text
手环夜跑数据异常
```

关卡定位：

```text
综合诊断关 / 第 11 章知识点二次巩固
```

## 2. 和第 1 关的关系

第 1 关已经建立了这些能力：

- 固定路径、固定塔位、圆形建造菜单。
- 4 类塔和 4 类敌人的克制关系。
- 正确克制增伤，错误应对大幅降伤。
- 波后诊断和波间答题解锁。
- 敌人症状动画和临时素材。

第 2 关不重做这些基础能力，而是复用它们，并新增少量关卡导演能力：

- 波前提示：用症状文字提示本波主要问题。
- 混合波次：每波都有主症状和少量干扰症状。
- 精英敌人：最后一波出现会切换异常类型的综合异常包。
- 诊断评分：结算时强调匹配命中率、错配命中、漏防类型。

## 3. 设计取舍

本关考虑过三个方向：

| 方向 | 内容 | 优点 | 问题 |
| --- | --- | --- | --- |
| 数值加压 | 更多敌人、更高血量、更快速度 | 实现最便宜 | 容易变成刷怪，不能更好考察知识点 |
| 新塔新地图 | 加 PPG 塔、新路线、新地图 | 新鲜感强 | 当前灰盒阶段范围过大，容易引入 UI 和资产债 |
| 综合诊断 | 症状提示、混合波次、精英切换类型 | 最贴合教学目标，复用现有机制 | 需要给波次和诊断加少量结构 |

推荐并采用“综合诊断”方向。

## 4. 核心玩法

玩家进入第 2 关后，看到同一张手环数据链路地图，但场景主题改为夜跑模式。系统在每波开始前给出一句症状描述，玩家需要判断这一波主要异常来自哪个知识模块。

示例：

```text
步数突然偏大，但 I2C 读数稳定。
```

这句话不直接说敌人类型。玩家应推断主要问题可能是噪声或假峰值，而不是 I2C 配置错误。

关卡仍然使用 4 类塔：

- I2C 初始化塔：应对配置错误。
- 滤波塔：应对噪声和抖动。
- 峰值检测塔：应对假峰值和重复计步。
- 低功耗塔：应对功耗尖峰和唤醒策略问题。

## 5. 波次设计

第 2 关建议仍为 3 波，控制时长和灰盒复杂度。

| 波次 | 波前症状 | 主异常 | 干扰异常 | 教学目的 |
| --- | --- | --- | --- | --- |
| 1 | 夜跑开始后，步数偶尔跳变，但设备连接正常。 | `noise` | `config` 少量 | 区分滤波问题和 I2C 配置问题 |
| 2 | 每次手臂大幅摆动后，步数会短时间连跳。 | `false_peak` | `noise` 少量 | 区分噪声抑制和峰值防抖 |
| 3 | 设备静止时耗电异常，恢复运动后又夹杂步数误判。 | `power_spike` + 精英综合异常包 | `false_peak`、`config` 少量 | 综合判断低功耗、唤醒和计步算法 |

建议数据：

```json
[
  {
    "wave": 1,
    "brief": "夜跑开始后，步数偶尔跳变，但设备连接正常。",
    "focusType": "noise",
    "enemies": [
      { "type": "noise", "count": 5 },
      { "type": "config", "count": 2 }
    ]
  },
  {
    "wave": 2,
    "brief": "每次手臂大幅摆动后，步数会短时间连跳。",
    "focusType": "false_peak",
    "enemies": [
      { "type": "false_peak", "count": 5 },
      { "type": "noise", "count": 3 }
    ]
  },
  {
    "wave": 3,
    "brief": "设备静止时耗电异常，恢复运动后又夹杂步数误判。",
    "focusType": "power_spike",
    "enemies": [
      { "type": "power_spike", "count": 4 },
      { "type": "false_peak", "count": 3 },
      { "type": "config", "count": 2 },
      {
        "type": "hybrid_fault",
        "count": 1,
        "switches": [
          { "progress": 0.0, "type": "power_spike" },
          { "progress": 0.45, "type": "false_peak" }
        ]
      }
    ]
  }
]
```

## 6. 精英敌人：综合异常包

`hybrid_fault` 是第 2 关唯一新增敌人概念。它不是第 5 类知识点，而是已有异常的组合体。

行为：

- 初始表现为 `power_spike`，弱点是低功耗塔。
- 移动到路径中段后切换为 `false_peak`，弱点变为峰值检测塔。
- 切换时播放一次明显脉冲或闪烁，提示玩家异常类型变化。

教学目的：

- 让玩家理解真实系统故障可能分阶段出现。
- 强化“低功耗策略”和“计步防抖”是两个不同模块。
- 避免玩家只靠单一塔型解决全部问题。

MVP 实现时不需要新素材，可以复用当前敌人动画，按当前 `type` 切换贴图、颜色、症状特效和 `threatTag`。

## 7. 波前提示

新增一个轻量 `wave_brief_label` 或复用右侧诊断区域，在每波开始前显示当前症状。

显示规则：

- 第 2 关每波开始时显示 `brief`。
- 波进行中仍保留提示，避免玩家漏读。
- 波后诊断替换为本波表现总结。

文案不直接暴露答案：

| 直白答案式 | 推荐症状式 |
| --- | --- |
| 本波主要是噪声敌人 | 步数偶尔跳变，但设备连接正常 |
| 本波需要峰值检测塔 | 手臂摆动后步数短时间连跳 |
| 本波是低功耗敌人 | 静止时耗电异常，运动后恢复工作 |

## 8. 诊断与评分

第 2 关的结算要更像学习诊断，而不是单纯胜负。

保留第 1 关已有统计：

- `matched_hits`
- `mismatched_hits`
- `kills`
- `leaks`

新增关卡级派生指标：

```text
匹配率 = matched_hits / (matched_hits + mismatched_hits)
主症状处理率 = focusType kills / focusType spawned
薄弱模块 = leaks 和 mismatched_hits 最高的异常类型
```

结算文案示例：

```text
夜跑诊断完成
匹配率：82%
主要薄弱点：峰值防抖
建议复习：最小步间隔和合加速度峰值判断。
```

如果匹配率低但通关成功，系统应提示：

```text
你靠火力通过了关卡，但多次使用了不匹配的塔。下一次试着先读症状，再决定建塔。
```

## 9. 答题设计

第 2 关题目继续覆盖第 11 章综合知识点，但题目更偏诊断语境。

建议新增 6 道题：

| 模块 | 题目方向 | 解锁或奖励 |
| --- | --- | --- |
| I2C | WHO_AM_I 正常但数据异常时，优先排查什么 | I2C 塔能量奖励 |
| I2C | ODR 配置过低/过高的影响 | I2C 塔强化 |
| 滤波 | 噪声导致步数跳变时，滤波的作用 | 滤波塔解锁或升级折扣 |
| 峰值 | 最小步间隔为什么能防止重复计步 | 峰值检测塔解锁或升级折扣 |
| 峰值 | 合加速度为何能降低佩戴方向影响 | 峰值检测塔强化 |
| 低功耗 | WOM 和 STOP 模式如何配合 | 低功耗塔解锁或升级折扣 |

题目仍采用现有结构：

```json
{
  "id": "ch11-night-run-peak-interval-001",
  "module": "step",
  "knowledgePoint": "最小步间隔防抖",
  "prompt": "夜跑时一次大幅摆臂后步数短时间连跳，最直接的算法修正是什么？",
  "choices": [
    "设置最小步间隔，避免同一次摆动重复计步",
    "跳过 WHO_AM_I 检查",
    "提高 OLED 亮度",
    "永久关闭加速度计"
  ],
  "answerIndex": 0,
  "explanation": "最小步间隔相当于时间防抖，可以避免同一次运动峰值被重复计为多步。",
  "unlockTag": "peak"
}
```

## 10. 数据结构变更

为了实现第 2 关，建议对波次 JSON 做向后兼容扩展。

当前结构：

```json
{ "wave": 1, "enemies": [{ "type": "noise", "count": 3 }] }
```

扩展后：

```json
{
  "wave": 1,
  "brief": "夜跑开始后，步数偶尔跳变，但设备连接正常。",
  "focusType": "noise",
  "enemies": [
    { "type": "noise", "count": 5 }
  ]
}
```

敌人条目保持兼容：

```json
{ "type": "noise", "count": 5 }
```

精英敌人条目新增可选 `switches`：

```json
{
  "type": "hybrid_fault",
  "count": 1,
  "switches": [
    { "progress": 0.0, "type": "power_spike" },
    { "progress": 0.45, "type": "false_peak" }
  ]
}
```

如果 `brief`、`focusType`、`switches` 缺失，旧关卡行为不变。

## 11. Godot 改动边界

本关实现时建议控制在以下范围：

- `data/waves.sample.json` 或新增 `data/waves.level2.json`
- `data/questions.sample.json` 或新增 `data/questions.level2.json`
- `scripts/band_defense_root.gd`
- `scripts/wave_diagnostics.gd`
- 对应测试脚本

不建议在第 2 关实现阶段做：

- 新地图系统。
- 新塔类型。
- 完整升级树。
- 商店或养成系统。
- 正式美术替换。
- 课程侧知识包抽离。

这些可以作为第 2 关稳定后的下一阶段。

## 12. 状态流

第 2 关推荐状态流：

```text
进入关卡
  -> 显示第 2 关标题和初始说明
  -> 点击开始
  -> 显示第 1 波症状提示
  -> 玩家建塔
  -> 波次运行
  -> 波后诊断
  -> 波间答题
  -> 下一波症状提示
  -> 第 3 波综合异常包
  -> 结算学习诊断
```

如果继续沿用第 1 关“开始后自动进入第 1 波”的方式，也可以接受。关键是每波开始前必须能看到 `brief`。

## 13. 测试策略

建议最少覆盖这些测试：

1. 波次 JSON 兼容旧格式：没有 `brief`、`focusType`、`switches` 时仍能运行。
2. 波前提示读取正确：第 2 关每波开始时显示对应 `brief`。
3. 精英敌人切换：路径进度达到阈值后，`type`、`threatTag`、弱点和视觉反馈同步切换。
4. 诊断统计：匹配率、主症状处理率、薄弱模块计算正确。
5. 第 1 关回归：旧三波 MVP 不受第 2 关扩展影响。

手动验收建议：

- 在 Web 导出中完成第 2 关 3 波。
- 至少建错一次塔，确认错配诊断能显示。
- 在第 3 波观察综合异常包切换后，确认塔的克制关系随之改变。
- 答题后能继续进入下一波或正常结算。

## 14. 成功标准

第 2 关完成后，应满足：

- 玩家能在不看敌人类型代码的情况下，通过症状提示判断主要问题。
- 错建塔会明显降低效率，并在波后诊断中被指出。
- 综合异常包能让玩家感知“同一设备问题可能跨模块变化”。
- 关卡仍保持灰盒 MVP 的可玩时长和可维护范围。
- 第 1 关现有交互、建塔菜单、答题、诊断和 Web 导出不回退。

## 15. 后续扩展

第 2 关稳定后，可以再考虑：

- 把第 1 关和第 2 关拆成可选择的 level 数据。
- 增加 PPG 干扰作为第 3 关核心。
- 将题库从 Godot 工程内迁移到课程侧知识包。
- 给不同关卡提供轻量难度参数。
- 再做正式 UI 和关卡选择界面。

这些不进入本次第 2 关实现范围。
